# 万能格式转换器 6–8 周项目改进设计

- 日期：2026-08-08
- 资源：1 人全职
- 周期：6–8 周
- 策略：冻结新增转换功能，均衡提升转换可靠性、商业交付体验与工程治理

## 1. 背景与决策

项目已经具备在线版、Tauri 离线版、EdgeOne 授权后台、离线授权、安装包分发、隐私检查和较完整的测试体系。本周期不扩展产品边界，而是提高现有能力的确定性。

仓库调查得到以下基线：

- 当前开发环境执行测试时共有 141 项通过、2 项跳过；被跳过的是 Word 和 Excel 的真实渲染测试。
- 本次调查环境为 Node 26，不是正式发布要求的 Node 20，因此结果只作为开发态参考。
- `ToolsClient.tsx` 约 2,888 行，`LocalToolsClient.tsx` 约 1,310 行，`globals.css` 约 10,000 行，文件输入、任务调度、转换执行、结果写入和界面状态存在集中耦合。
- 现有测试中包含较多源码字符串断言，适合守住静态边界，但不足以证明真实文件转换成功。
- Windows 安装包尚未代码签名，授权后台允许 6 位数字密码且没有失败锁定或速率限制。

本设计选择“质量底座优先，再打通商业闭环”的路线。原因是项目价值链依次为：用户找到工具、文件成功转换、相信文件未上传、下载离线版、顺利安装激活、维护成本可控。新增格式不会修复这条链路中的失败点。

## 2. 目标与非目标

### 2.1 目标

1. 真实文件转换结果可重复验证，关键 Office 测试不再长期跳过。
2. 损坏文件、不支持格式、内存不足、转换引擎失败和写入失败都有明确阶段、后端和用户操作建议。
3. 固定 Node 20、pnpm 9.15.4 与 Rust 工具链，一条发布门禁覆盖测试、隐私、网络、构建、安装包和秘密泄漏检查。
4. 在线下载、断网安装、首次转换、3 天试用、机器码和离线激活形成可验收闭环。
5. UI 不再直接承担文件识别、任务调度、引擎选择、转换执行和结果写入的全部职责。

### 2.2 非目标

- 不新增转换格式或工具。
- 不新增登录、注册、会员、支付、联网授权或云端转换。
- 不上传用户文件、Canvas、Blob、ArrayBuffer、转换结果或文件遥测。
- 不进行全站视觉重构，不改变 LOGO、隐私原则、权限模型和本地处理原则。
- 不建立面向未来的插件平台，不清理与本周期无关的代码。
- 不改变离线批量结果的独立文件夹规则，也不回退为 ZIP 或 7Z 汇总。

## 3. 成功标准

本周期使用以下记分卡验收：

| 维度 | 完成标准 |
| --- | --- |
| 真实转换 | 固定样本矩阵中的预期成功或预期失败结果全部通过；Office 关键路径没有跳过项 |
| 失败处理 | 受控失败场景均返回错误代码、失败阶段、执行后端和用户操作建议 |
| 隐私 | 现有隐私与网络检查通过，浏览器和桌面流程没有用户文件外传 |
| 发布 | Node 20 环境中的统一发布门禁通过，版本、产物内容和 SHA256 一致 |
| 离线交付 | 干净 Windows 10/11 x64 虚拟机可断网安装、转换、批量输出和激活 |
| 商业流程 | 下载说明、试用状态、机器码、激活和常见错误形成连续路径 |
| 可维护性 | 修改单个转换流程不再要求同时修改文件输入、任务状态、后端选择和结果 UI |

真实样本矩阵首版至少包含 20 个可公开或项目自制的无敏感文件：图片 4 个、PDF 4 个、Word 3 个、Excel 3 个、音视频 4 个、OCR 2 个。矩阵覆盖正常、复杂、超大、损坏和不支持输入；断言以页数、尺寸、格式、时长、编码、音轨和关键文本等稳定属性为主，不比较不稳定的完整输出哈希。

## 4. 目标结构与数据流

系统保留现有 `image-core`、`pdf-core`、`media-core`、`ocr-core`、`export-core` 和 Tauri 本地能力，只增加轻量的转换任务契约和适配边界。

```text
文件输入
  → 统一转换任务
  → 引擎选择
     ├─ 浏览器本地 WASM
     ├─ Tauri FFmpeg sidecar
     └─ Tauri LibreOffice
  → 统一结果与错误模型
  → Web 下载 / Tauri 文件夹写入
  → UI 状态展示
```

统一任务至少包含 `id`、`tool`、`inputs`、`options`、`surface` 和 `outputTarget`。状态只允许按以下路径变化：

```text
queued → inspecting → ready → running → writing → completed
                              ├→ failed
                              └→ cancelled
```

组件职责如下：

- 文件输入层：选择文件、识别类型、收集元数据和生成预览信息。
- 工具执行层：每个工具保留独立执行函数，调用现有核心包。
- 桌面适配层：处理 FFmpeg sidecar、LibreOffice、Tauri 路径和文件写入。
- Web 适配层：处理浏览器内存、Blob 结果和本地下载。
- 任务控制层：管理状态、进度、取消、批量顺序和错误归一化。
- UI 层：读取任务和授权状态并呈现，不自行决定执行后端。

引擎规则保持显式：Office 桌面任务使用 LibreOffice；桌面媒体任务在本地路径可用时使用 FFmpeg sidecar；其他场景沿用浏览器本地实现。不引入动态插件或运行时注册系统。

## 5. 错误、取消与输出一致性

统一错误包含：

- `code`：稳定错误代码；
- `stage`：读取、预览、转换、写入或授权；
- `backend`：WASM、sidecar、LibreOffice 或浏览器；
- `message`：面向用户的简短说明；
- `action`：重新选择文件、释放空间、缩短视频或检查输出目录等操作建议；
- `cause`：仅供本地开发诊断，不发送到外部。

批量任务中单个文件失败不终止其他文件。桌面结果先写入任务专用临时名称，完整成功后再确定最终名称；失败或取消时清理本任务创建的临时文件，不删除用户已有文件。取消还必须释放 Object URL、WASM 内存和进程资源。

Web 文件只存在于浏览器内存；桌面路径只传给 Tauri 本地命令。日志和诊断摘要不记录完整路径、文件内容、客户名称、机器码、授权码或私钥。

## 6. 测试设计

### 6.1 纯逻辑单元测试

覆盖任务状态、引擎选择、输出命名、页码解析、批量计数、取消和错误归类。

### 6.2 转换契约测试

每个工具验证合法输入、进度、取消、有效输出、结构化失败和无网络上传。现有源码字符串断言继续守住隐私、权限与打包边界，但关键用户行为必须有行为测试。

### 6.3 真实样本测试

- 图片：尺寸、格式、透明度和目标体积区间。
- PDF：页数、输出张数和页面尺寸。
- Word/Excel：第一页可渲染，页数或工作表输出正确。
- 音视频：编码、时长、分辨率和音轨。
- OCR：预先定义的关键文本命中。

无法在普通 Vitest 环境执行的 Office 测试进入 Node 20 与固定 LibreOffice 版本的专用验证任务。关键转换测试被跳过时，正式发布门禁失败。

### 6.4 浏览器与桌面流程测试

覆盖文件选择、预览、参数、转换、取消、批量结果、下载、试用锁定和激活。桌面静态壳测试保留，同时增加真实 Tauri 命令与文件系统验证。

### 6.5 发布门禁

新增并固定使用单一入口 `npm run verify:release`，顺序执行：

```text
Node 20 / pnpm 9.15.4 检查
→ 单元与集成测试
→ 隐私与网络边界检查
→ Cargo check/test
→ Web 与 EdgeOne 构建
→ 安装包内容、版本、分片和 SHA256 检查
→ 私钥、客户记录和 .mrx 泄漏扫描
```

性能使用固定样本和固定标准机器记录基线。同一机器、同一工具链出现显著回退时阻止发布；首版阈值采用连续三次运行中位数较已批准基线上升 20%。

## 7. 下载、试用与授权交付

下载页首屏明确说明离线版用途、与在线版的区别、本地处理原则、Windows 要求和 3 天试用。主下载按钮附近展示版本、文件大小和发布日期；SHA256、分片与完整性说明放入展开区域。

SmartScreen 风险在下载前说明并提供图文步骤。第一周决定是否采购 Windows 代码签名；采购不会阻塞其他任务。若本周期不签名，继续公开校验值和安装说明，不弱化风险提示。

离线版首次启动仍直接进入工作台。试用期内在状态栏克制显示剩余天数，不遮挡转换；到期后只锁定执行动作，机器码查看、激活码输入和授权文件导入保持可用。

授权流程固定为：复制机器码、联系管理员、收到激活码或 `license.mrx`、粘贴或导入、本地验签、返回原任务。错误明确区分格式错误、签名无效、机器码不匹配、授权过期、系统时间异常和文件损坏。

授权后台继续作为单管理员私有工具，不扩大为用户账号系统。必须把同源检查应用到所有受保护接口。相同客户端标识在 15 分钟内最多允许 5 次失败登录，之后返回 HTTP 429，窗口结束后恢复；限制状态保存在服务端且不记录明文密码。具体由 EdgeOne 入口规则或函数端存储实现，但两种实现必须通过同一组行为测试。

本地诊断摘要属于条件完成项，只包含应用版本、Windows 版本、执行后端、错误代码和失败阶段，不包含用户文件或授权信息。

## 8. 6–8 周路线

### 第 1 周：可靠性基线

- 固定发布工具链并建立真实样本矩阵。
- 记录当前结果、耗时、输出结构和已知偏差。
- 将现有测试分类为行为测试、源码断言和边界检查。
- 恢复或拆分 Word、Excel 真实渲染验证。
- 决定是否采购 Windows 代码签名。

### 第 2–3 周：转换主链路

按 Word/Excel/PDF 多页输出、桌面批量结果、FFmpeg sidecar 与 WASM 回退、大文件与取消、OCR 与图片边界的顺序处理。同步落地统一任务状态和错误模型。

### 第 4 周：代码边界

从巨型 UI 组件抽出任务控制、引擎选择、结果写入和错误归一化。相关 CSS 按产品壳与组件拆分。不改变已批准的在线与离线视觉方向。

### 第 5 周：试用与商业交付

完善下载页、SmartScreen 说明、试用状态、机器码、激活和授权错误；加入授权后台防暴力尝试措施。若代码签名采购完成，将签名接入发布流程。

### 第 6 周：发布工程

建立统一发布门禁，验证 ZIP、MSI、分片清单、版本和 SHA256；在干净 Windows 10/11 虚拟机执行断网验收。

### 第 7–8 周：缓冲与验收

只修复样本、虚拟机和发布演练暴露的问题。前六周全部完成后，才处理诊断摘要、性能基线扩充和更多源码断言替换。

## 9. 优先级与截断规则

必须完成：工具链固定、真实样本、关键路径行为测试、统一状态与错误、主链路解耦、发布门禁、断网验收、下载试用激活闭环、授权后台跨域与防暴力保护。

条件完成：代码签名、本地脱敏诊断摘要、性能样本扩充、更多字符串断言替换、进一步拆分全局 CSS。

当进度落后时，依次放弃条件完成项，不削减真实转换验证、隐私边界、发布完整性或断网激活验收。同时只推进一条主链路，每周末保留可运行、可回退的版本。

## 10. 风险控制

- Office 输出差异：固定 LibreOffice 版本，验证稳定属性而非完整文件哈希。
- 巨型组件拆分回归：逐个职责迁移，每次迁移后运行原测试和对应真实样本，不一次性重写。
- 安装包大、构建慢：第三方资源按版本和 SHA256 缓存，正式门禁只接受已验证资源。
- 代码签名等待：第一周完成采购决策，其他主线继续推进。
- 单人工作量：限制同时进行的工作，每周产生可验收结果。
- 管理后台口令风险：优先添加速率限制或平台入口控制，不扩展为会员认证系统。

## 11. 最终验收场景

在固定 Node 20 环境完成统一发布门禁，然后在未安装项目开发依赖的干净 Windows 10 和 Windows 11 x64 虚拟机中分别执行：下载正式 ZIP、核对 SHA256、断网安装、启动试用、处理真实图片/PDF/Office/音视频样本、执行批量输出、验证独立结果文件夹、模拟失败和取消、复制机器码、输入激活码、导入 `license.mrx`、重启后确认授权仍有效。

只有关键样本无跳过、失败可解释、用户文件无外传、产物一致且两套虚拟机流程均通过，才视为本周期完成。
